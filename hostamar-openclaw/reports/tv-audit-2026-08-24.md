## 2. Existing TV Capability (a LOT already built)

### Streaming core — `lib/tv/streamer.ts`
- `buildFfmpegCommand(playlistFile, destinations)` — builds one ffmpeg process,
  `-re -stream_loop -1`, x264 2500k, then tee-style `-f flv <rtmpTarget>` per
  destination → **multi-platform simulcast is already implemented**.
- `buildRtmpTarget()` handles YouTube (`rtmp://a.rtmp.youtube.com/live2/KEY`)
  and Facebook (`rtmps://live-api-s.facebook.com:443/rtmp/KEY`) formats.
- `seedDestinationsFromEnv()` auto-seeds YOUTUBE/FACEBOOK/TWITCH destinations
  from env vars when DB is empty.
- `.env.example` already documents: `YOUTUBE_RTMP_URL`, `YOUTUBE_STREAM_KEY`,
  `FACEBOOK_RTMP_URL`, `FACEBOOK_STREAM_KEY`, `TWITCH_*`, `TV_RTMP_URL`.

### Agent-side restream fanout — `scripts/tv/restream.py`
Reads active `TvStreamDestination` rows, pulls `rtmp://127.0.0.1:1935/live/tv`,
tee-copies to every destination with `-c copy` (no re-encode). Designed for
100+ destinations, runs as a systemd service, sleeps when none enabled.
**This is the missing link between the local TV station and YT/FB — it just
needs real stream keys and a systemd enable.**

### API surface — 23 `/api/tv/*` routes (of 66 total API dirs)
agent/ack, agent/commands, agent/destinations, agent/opensource-report,
credits, destinations, epg.xml, generate, generate-loop, hls-url,
hunter/tool/search, iptv.m3u, now-playing, playlist, **restream**, status,
**stream/start**, **stream/stop**, view, viral/create, viral/create-now,
viral/research, viral/top

### DB models (prisma/schema.prisma, created at runtime by ensureSchema)
TvChannel, TvPlaylistItem, TvStreamDestination (platform/rtmpUrl/streamKey/
isActive/lastError), TvSchedule, TvSettings, TvCommand, TvLog, TvVideoSeo,
TvVideoStats.

### Security posture (verified)
- No hardcoded stream keys anywhere (only placeholder docs text).
- Agent routes guarded by `TV_AGENT_SECRET`; admin UI masks keys (`abcd…wxyz`).
- Keys belong in Vercel env / GitHub Secrets — pattern already documented.

### Supporting assets
- Live infra TODAY: local nginx-rtmp→HLS at tv.hostamar.com (200), VP9 variant,
  CC0 slow-net library (9 ad-burned files, all 6 products), tv-pure.timer 6h,
  health-check auto-heal timer, IPTV playlist `/api/tv/iptv.m3u` (#EXTM3U+CORS).

- `marketing-engine.py` (46 fb/yt mentions): social posting — could cross-post

## 3. What's MISSING for 24/7 YouTube + Facebook (hybrid)

1. **Real stream keys** — `YOUTUBE_STREAM_KEY` / `FACEBOOK_STREAM_KEY` empty.
2. **restream systemd unit not enabled** — script exists, never wired as
   `tv-restream.service` on the PC (the earlier `tv-restream.service` name
   referenced in old prompts never existed).
3. **Hybrid heartbeat** — nothing monitors "PC alive?" and flips YT/FB ingest
   between PC source and a cloud source. No watchdog, no DNS/ingest switch.
4. **Cloud fallback source** — if PC dies, YT/FB need *some* RTMP feed. Nothing
   cloud-side can currently produce one.
5. **GitHub Actions streaming workflow** — none exists (and see risk §6).

## 4. Three-step plan (100% open-source)

### Step 1 — Wire keys + enable PC fanout (PC ON path, ~30 min, zero cost)
1. Put keys in Vercel env + local `.env.local`:
   `YOUTUBE_STREAM_KEY=xxx-xxx-xxx`, `FACEBOOK_STREAM_KEY=…`
   (YouTube: create live stream → "Stream key"; FB: Live Producer → persistent key.)
2. `POST /api/tv/restream {platform:'YOUTUBE'|'FACEBOOK', rtmpUrl, streamKey}`
   once each (or let `seedDestinationsFromEnv` do it).
3. Create `~/.config/systemd/user/tv-restream.service` running
   `scripts/tv/restream.py` (Restart=always) + `loginctl linger` (already on).
   PC ON ⇒ YT+FB get the same CC0 slow-net channel via `-c copy`.

### Step 2 — Heartbeat + hybrid flip (~1 day)
1. New route `GET /api/tv/heartbeat` (public, cached): returns `{pcLive:true}`
   true only when local HLS has fresh segments (<20s old) — reuse
   `getStreamStatus()`'s hlsReachable + segment mtime check.
2. New GitHub Action `.github/workflows/tv-cloud-fallback.yml` on
   `schedule: * /5 * * * *`:
   - probe `tv.hostamar.com/hls/tv/index.m3u8` freshness;
   - if STALE ≥2 consecutive runs AND secrets exist → start a self-hosted-style
     relay job: ffmpeg `-re -i <cloud playlist URL> -c copy -f flv $YT_KEY/$FB_KEY`;
   - if FRESH → ensure its own previous streams stopped (idempotence file in
     Actions cache or check YT API).
3. Cloud playlist source when PC is OFF: a small static HLS generated at deploy
   time from the CC0 library (files ≤60MB) hosted on Vercel/Cloudflare Pages —
   ffmpeg in the runner loops it into YT/FB.

### Step 3 — Keep-alive & observability (~half day)
1. Extend existing `tv-health-check.timer` to also verify YT/FB ingest health
   (via `TvStreamDestination.lastError` written by restream.py).
2. Telegram alert on destination failure (token/chat already used elsewhere).
3. Optional: `marketing.yml`-style daily post "🔴 LIVE now on YouTube/FB".

Files to create/modify:
- new: `~/.config/systemd/user/tv-restream.service` (host, not repo),
  `.github/workflows/tv-cloud-fallback.yml`, `app/api/tv/heartbeat/route.ts`,
  `scripts/cloud-playlist-gen.mts` (build static HLS from pure/)
- modify: `scripts/tv/restream.py` (add heartbeat writes to lastError),
  `docs/TV_HYBRID_247.md`

## 6. Risks (honest)

| Risk | Detail | Mitigation |
|---|---|---|
| **GitHub ToS** ⚠️ | Actions AUP forbids using runners for activity "unrelated to software production" — 24/7 media streaming is a classic ban trigger even on public repos (unlimited minutes ≠ unlimited purpose) | Prefer Step 2's *conditional* fallback (runs only while PC is down, minutes ≈ downtime). Do NOT run a permanent 24/7 streamer in Actions. If PC-off coverage becomes permanent, move to a ~$4-5/mo VPS or Oracle free tier instead |
| Bandwidth (PC) | `-c copy` fanout ≈ upload = 1× bitrate × N destinations ≈ 2.5Mbps × 2 ≈ 5Mbps up — fine on BD broadband, tight on mobile hotspot | Keep slow-net 900k encode; cap destinations ≤4 |
| Storage | archive_heavy 2.7GB + viral_archive 219GB-scale creep | Already archived; delete when confirmed |
| Secrets exposure | YT/FB stream keys in DB (plaintext `streamKey` column) + Vercel env | DB is Neon (private); admin UI masks; agent route requires TV_AGENT_SECRET; never log full targets |
| YT/FB policy | Re-broadcasting NASA/Prelinger is safe (PD); Blender films need attribution line in description | Add credits text to stream descriptions via restream metadata |

## 7. Bottom line
~80% of the 24/7 YT+FB stack already exists in-repo (fanout engine, DB models,
APIs, agent auth, IPTV, live HLS). The gap is operational, not architectural:
keys → `tv-restream.service` on PC (Step 1, today) → conditional Actions
fallback for PC-off (Step 2) → monitoring (Step 3). Avoid permanent Actions
streaming to stay inside GitHub ToS.
